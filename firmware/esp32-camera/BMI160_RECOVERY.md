## 已實際做過甚麼

1. 用戶重新插牢 S3 的 CH340C 旁 COM 接口和電腦端；Windows 再次出現 COM9／CH340，能讀到網關 INFO。
2. 完整斷電／重新插牢之後，啟動仍讀到 BMI160 0x68／0xD1；失敗階段為 `GYRO_WAKE_WRITE`，代表送出喚醒陀螺儀命令時 I²C 寫入回傳非零。未建立採集工作，sample count=0、fault=4。
3. 新增只允許初始化失敗、尚無採集工作時執行的 `IMU_BUS_DIAG`。所有寫入只是既有的軟重設及 PMU 命令，沒有寫入 NVM／eFuse。
4. 同一故障總線上比較 20ms 與 100ms 等待上限；結果見下表。100ms 案例接在已失去通訊的狀態之後，不能當成乾淨的獨立對照。
5. 再將開機流程直接改用原六軸基線的 100ms，重新編譯／上傳／重啟。INFO 明確讀回 i2c_timeout_ms=100，但仍 imu=FAULT、fault=4、total_samples=0，未恢復。

| 案例 | 實測 |
| --- | --- |
| 20ms：軟重設 0xB6 | code=0，529 µs |
| 20ms：喚醒加速度計 0x11 | code=0，359 µs |
| 20ms：喚醒陀螺儀 0x15 | code=4，6,987 µs；之後身份／PMU／錯誤暫存器均讀取失敗 |
| 接續的 100ms：軟重設 | code=4，99,722 µs；身份／PMU／錯誤暫存器讀取失敗 |
| 從重新開機即用 100ms | 仍初始化故障，沒有有效六軸資料；本段 INFO 未保留失敗點之前的全部開機行，不將它說成已重新逐點證明同一階段 |

Wire code=4 是本機 core 3.3.12 的一般其他錯誤，明確 timeout 對應 code=5；不能單憑 code=4 判定是逾時，也不能據此判定模組壞了。100ms 從開機測試仍未恢復，尚無證據支持「單純把等待時間改長便修好」。

上述網關診斷來源保留 100ms，沒有宣稱它是已驗證修復；完整照片／IMU 工具會拒絕 FAULT。後續已恢復 11-04 原成功映像，現在板上版本及最新結果見文末「原成功固件對照」。
